## Domain Notes
- Normal command targeting by room name depends on discovery; SSDP currently uses one wildcard-bound UDP socket, so multicast egress follows a single route/interface.
- Discovery's last-resort scanner enumerates a synthetic `/24` per local IPv4 address rather than each interface's actual CIDR.
- `watch` receives a parsed subscription lease (commonly 1800s) and the Sonos client already implements `Renew`, but the CLI never renews, so indefinite watches silently stop receiving after lease expiry.
- `Subscription.Timeout == 0` currently conflates an `infinite` lease with a missing/malformed `TIMEOUT` header because `Subscribe`/`Renew` discard `parseSecondTimeout`'s validity result; renewal work must preserve that distinction or explicitly define the fallback.
- The authoritative checkout is `/Users/daveashworth/data/projects/sonoscli`; sibling `/Users/daveashworth/data/projects/sonos-cli` is not a Git repository.
- Every normal coordinator-based `--name` command performs full SSDP/topology discovery, then fetches topology again; the persisted cache stores completion names only. Docs incorrectly claim fresh cached topology lets subsequent commands skip discovery.
- On the available live network, the installed 0.1.0 binary measured `status --name Office` at 1.76–1.97s versus 0.07–0.09s with `--ip`; current source retains the same full-discovery name path.
- After adding a validated 5-minute discovery-foothold cache, the current 0.3.5 source measured a 2.58s cold `status --name Office` and 0.10–0.18s warm runs; debug output confirmed warm runs made no SSDP/discovery calls and still fetched fresh topology.
